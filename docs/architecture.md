# Architecture

Single user, localhost only, no authentication, no deployment. Those absences are
deliberate and load-bearing — most of the simplicity here follows from them.

## Request flow

```
browser :5173  ──/api/*──>  Vite dev proxy  ──>  Hono :8787
                                                     │
                                    ┌────────────────┼────────────────┐
                                    ▼                ▼                ▼
                              content.db      characters.db     homebrew.db
                              (raw SQL)         (Drizzle)        (Drizzle)
```

`packages/shared` is imported by both `api` and `web`: Zod schemas, the tag parser, the
dice engine, and rules arithmetic all need to run on both sides of the wire. That shared
package is the main reason the backend is TypeScript.

## Three databases

Splitting these is the central design decision.

| | Owner | Migrated | Backed up |
|---|---|---|---|
| `content.db` | generated by ETL | **never** — rebuilt wholesale | no, regenerable |
| `characters.db` | the user | yes, Drizzle | yes |
| `homebrew.db` | the user | yes, Drizzle | yes |

Because the catalog is disposable, `rm data/content.db && pnpm content:build` is always
safe. Mixing user data into it would make that false.

Characters store *references* to catalog rows — `{name, source}` — never copies. A
rebuilt catalog therefore updates every character automatically. Only homebrew is stored
by value, because nothing else owns it.

`content.db` uses raw SQL rather than Drizzle. It has no migrations to generate, and its
FTS5 queries are awkward to express through an ORM. That also limits how much of the
codebase depends on Drizzle, which is the highest-churn dependency here.

## Content tiers

The catalog is loaded at three levels of fidelity, so importing everything stays
tractable without schema-ing 46 MB of adventure prose.

```
TIER A   bespoke tables, full schema, queried directly by the sheet
         classes · subclasses · class_resources · spell_slots · spells · items
         races · backgrounds · feats · optional_features

TIER B   thin lookup table, resolves {@tag} references and fills pickers
         conditions · statuses · skills · senses · languages · actions
         variant_rules · tables · deities · creatures · rewards · psionics

TIER C   one generic table for everything else, adventures and books included
         entities(type, name, source, edition, json, rendered_text) + FTS5
```

Tier C is what makes "import everything" possible. No `{@tag}` ever dangles, because an
unrecognized type still resolves to a name, a source, and body text. Everything is
searchable from day one. And promotion is incremental — moving a type from C to A means
a new table and a backfill, with no re-fetch.

## Character state

Two splits, both of which exist to make level-ups safe.

**Definition versus state.** `characters` holds who the character is; `character_state`
holds what is true right now — current hit points, spent slots, active conditions. A
long rest touches state only, so it can never corrupt the sheet.

**Computed versus manual.** Derived fields carry the computed value, an optional manual
override, and a flag. Recomputing on level-up updates the computed side and leaves
overrides intact. No rule ever hard-blocks a value the user insists on, which is what
makes the builder usable at a table with house rules.

Both logs are bounded and pruned on insert — 200 rolls and 50 undo entries per
character. They are session affordances, not audit trails.

## Deliberately absent

Listed so they do not get added back by reflex:

- **No authentication or user model.** One user, bound to `127.0.0.1`. Adding an owner
  column "for later" would be speculative.
- **No network access.** The API binds to loopback. Moving to LAN later is a bind
  address and a responsive layout, not a schema change.
- **No deployment, CI deploy step, or container.** Nothing is hosted; hosting WotC
  content publicly would be a legal problem, not just an infrastructure one.
- **No realtime or websockets.** A single client cannot conflict with itself.
- **No caching layer.** `better-sqlite3` reads are synchronous and local.
